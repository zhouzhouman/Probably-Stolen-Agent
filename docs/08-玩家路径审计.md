# 08 · 操作路径审计：玩家等价 vs 底层直调（2026-10-18）

> 设计原则（2026-10-18）：操作路径应当等价于**玩家能完成的动作**，而不是直接调用底层函数和变量。
> 后者会跳过正常流程，导致一系列问题——例如不经过睡眠直接进入次日、次日无法开门等。
> 本文档审计全部 35 个桥接动作的实现路径，分级定格，并把已暴露的 bug 对应到具体动作。

## 一、动作分级总览

判定标准：**玩家在游戏里能不能完成同一个操作**（点按钮/开面板/走 UI 链），以及实现
是否绕过 UI 与游戏状态机。

## 三、根因判断

1. **v0.9.0「UI 按钮化」只覆盖了 7 个高频动作**；之后新增的 begin_day /
   night_service / toggle_power / place_item 全是直调或字段写。
2. **end_day 按钮化有条件**：仅 store_state==OPEN 走按钮；CLOSED 时静默降级
   直调（r49 的 4 连打烊正是 CLOSED 分支）。
3. **直调没有流程状态机校验**：调完游戏进入什么状态、UI 是否响应，直调不保证。
4. 部分直调是历史上有意为之（place_item 的 v0.5.0「纯变量路线」按当时的设计约束
   「不模拟鼠标，直接控制游戏状态」）——现在该约束已反转，需要重新评估。

### 关键反汇编结论（可复用）
- `StoreShutterButton.OpenShutter()` = 玩家开张链路（含 OnShutterDoorOpenMorning）
- `StoreBedroll.OnClick()` = 玩家睡觉入口（打开 EndOfDay 面板）
- `NegociationUIManager.TrySellItem()` = 卖出按钮处理器；`BuildItem`/`BuyItem` = 买入按钮处理器；`OnOfferAcceptClick` 仅买入方向
- `StoreTransferButton.OnClick` = 转移所有物品（前台柜台→储物区），v0.9.18 已自动衔接

### 保留的直调（带校验兜底）
sell_item/buy_item 在面板链未成交时保留核心直调兜底（现金/钱货两清校验通过才认，detail 明确标注「已用核心直调兜底」）。
理由：面板按钮链依赖游戏内部 UI 状态（sellable 列表/谈判状态），纯 API 层无法完全复刻 Ctrl+点击的完整输入链（v0.5.0 已实证 PlacedItemFor*/AddDirectSellingItemToTable 静默 return）。带校验的兜底保证：**绝不静默脱节、绝不假成功**。
