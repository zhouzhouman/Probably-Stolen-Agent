### 1.2 关键判断：正式版是 Mono 后端，不是 IL2CPP

依据（均为文件系统事实，非推断）：

1. 正式版**没有** `GameAssembly.dll`，也**没有** `Probably Stolen_Data/il2cpp_data/`；
2. 正式版**有** `MonoBleedingEdge/`（含 `EmbedRuntime`、`etc`）；
3. 正式版**有** `Probably Stolen_Data/Managed/Assembly-CSharp.dll`（4.75 MB）等全套托管程序集；
4. 试玩版反过来：有 `GameAssembly.dll` + `BepInEx/` + `doorstop_config.ini` + `baselib.dll`，是标准 IL2CPP 布局。

这推翻了任务书第 2、3 步的技术前提（Il2CppDumper + BepInEx6 IL2CPP）。

### 1.3 正式版代码规模

用 `ilspycmd` 反编译 `Assembly-CSharp.dll`（输出 `tools/decompile_full/`，944 个文件）：

- **1060 个类型**、**约 24.5 万行 C#**（真实源码，含方法体，不是签名 dump）；
- 试玩版 `tools/Il2CppDumper/dump.cs` 为 532,489 行签名 dump（约 19 MB）。
- 两版**不能按行数直接比**：一份是签名清单，一份是含实现的源码。

### 1.4 存档目录冲突（需要处置）

`%USERPROFILE%/AppData/LocalLow/Questing Goose Studio/` 下**只有一个** `Probably Stolen/` 目录，
两版游戏名相同（`app.info` 均为 `Questing Goose Studio` / `Probably Stolen`），因此：

- 现有 `SaveFile.es3`、`save_0..26.es3` 等 44 个非日志文件是两版混用的；
- Easy Save 3 的键若在正式版有增删，可能读档报错或读到半残档；
- **风险**：AI 自主跑批时如果读错档，会污染真实存档。

处置建议：迁移期间先整目录备份到 `artifacts/save_backup_demo/`，再对正式版单独跑。

### 1.5 阶段小结

- **做了什么**：只读侦察两版安装目录、Steam 清单、存档目录、托管程序集，并反编译正式版全部游戏逻辑。

## §2 结构化 diff（重做第 2 步）

### 2.1 方法调整

原计划用 `Il2CppDumper` 重跑正式版再 diff `dump.cs`。正式版为 Mono，**不需要 dump**——
反编译得到的 C# 源码信息量严格更大（含方法体、含真实泛型与元组类型）。
因此 `scripts/diff_dump.py` 改为：试玩版 `dump.cs`（签名）↔ 正式版反编译源码（真实 C#），
做**成员名集合级**比对，字段/方法/属性分桶。

已知局限：签名 dump 与 C# 源码形态不同，存在假阳性——
`get_Foo()` 会还原成属性 `Foo`，编译器闭包 `b__xx_0`、`k__BackingField`、`ctor` 都是产物噪声，
元组类型字段（如 `List<(GameItem, Action)>`）也会漏解析。脚本已对前两类做归一化，
**最终以"能否编译通过"为唯一裁决**。

### 2.2 结果：51 个真实缺失（已剔除噪声），其中确认的实质变更

| 类型 | 变更内容 | 对桥接的影响 | 处理方式 |
|---|---|---|---|
| `MapUIManager` | `VisitScavenging`、`VisitUpgradeMerchant`、`Bazar`、`HandleLeaveScavenging`、`HandleLeaveUpgradeMerchant`、`HandleLeaveCommissary` **全部删除**；新增 `ScavengeButtonClick()`、`LeaveScavenging()`、`CommissaryTradeButton()`、`OpenGoOutsideConfirm()`、`OnGoingOutside()`、`OpenLocationPanel()`、`IsShowingGoOutsideConfirm()` | **拾荒与外出入口整条链路失效** | 属**机制变更**：改走新按钮方法，拾荒流程需在新 API 上重走一遍 |
| `MapUIManager` | `bazarButton`、`dumpingGroundButton`、`upgradeMerchantButton`、`currentLocation` 字段消失 | 地图按钮定位失效 | 改用 `UICommissaryPanel`/`UIScavengingPanel`/`UIUpgradeMerchantPanel` + `activePanelObject` |
| `GameItem` | `children` / `parents` 由**字段**变**属性**，且元素类型 `GameInventory` → **`GraphNodeStorage`** | 编译期类型不兼容 | `GameItem : GraphNodeStorage` 继承关系成立则多数调用点可直接沿用；否则需显式转换 |
| `GameItem` | `ComputeModifiedShapeState`、`GetParentShapeModifier`、`GetParentStateModifier` 消失 | 若桥接用到则失效 | 编译时确认，按新 API 改写 |

| `EmporiumEntry` | `choices` 报缺失 | **假阳性**：`EmporiumEntry.cs:28` 确实存在 `public List<(GameItem, Action)> choices`，元组类型未被正则识别 | 无需处理 |

### 2.3 阶段小结

- **做了什么**：改写迁移 diff 脚本为「签名 dump ↔ 真实源码」比对，产出成员级变更清单。
- **证据**：`scripts/diff_dump.py`、`artifacts/_migration_diff.json`、`tools/decompile_full/*.cs`。
- **未解决的风险**：名字级比对无法覆盖签名/类型变更（`GameItem.children` 这种就差点漏掉）；须以编译结果为准。
- **下一步**：把桥接改到 Mono/BepInEx 5 并编译，用编译器一次性暴露全部不兼容点。

## §3 架构结论（待确认）

### 3.1 桥接必须重写加载模型

现工程 `bridge/DeepSpaceBridge.csproj` 的引用全部指向 IL2CPP：

```
BepInEx.Unity.IL2CPP.dll        → Mono 下不存在
Il2CppInterop.Runtime.dll       → 不存在
BepInEx/interop/*.dll           → 不存在
```

对应代码改动：

| 位置 | 现状（IL2CPP） | 正式版（Mono） |
|---|---|---|
| `Plugin.cs` | `BasePlugin` + `ClassInjector.RegisterTypeInIl2Cpp<T>()` | `BaseUnityPlugin` + `AddComponent<T>()` |
| 程序集引用 | `BepInEx/interop/Assembly-CSharp.dll` | `*_Data/Managed/Assembly-CSharp.dll`（真程序集） |
| `BridgeApi.cs` | 32 处 `Il2Cpp*`、58 处 `TryCast`、2 处 `Il2CppStructArray` | 改为原生 C# 类型与直接转换 |
| `DecisionOverlay.cs` | uGUI + IL2CPP 注入 | uGUI 直接派生 `MonoBehaviour` |

**收益**：`Il2CppStructArray<Vector3>`、`TryCast` 失败静默、interop 类型不匹配这类坑整体消失。
**代价**：`BridgeApi.cs` 4189 行需要逐处去 IL2CPP 化，这是本次迁移的主要工作量。

### 3.2 待确认

## §4 改造为游戏原生 mod（用户 2026-11-07 指示）

### 4.1 结论

正式版自带完整的 mod 框架（`ModLoader` / `ModManifest` / `ModCapability` / `ModHook` /
`ModScanner` / `ModTrustList` + 随游戏分发的 `0Harmony.dll`），因此**不需要 BepInEx**：
把桥接编译成 mod DLL 丢进 `<游戏根>/Mods/` 即可。§3 里"装 BepInEx 5 + 去 IL2CPP 化"的方案作废。

### 4.2 框架事实（读源码 + 三个真实 Workshop mod 双向核对）

| 项 | 结论 | 依据 |
|---|---|---|
| mod 根目录 | `<游戏根>/Mods/<文件夹>/` | `ModLoader.ModsPath => Application.dataPath + "/../Mods"` |
| 声明文件 | `manifest.xml`（XML，不是 JSON） | `ModLoader.ParseManifestCore()` 用 `XDocument` 读 |

### 4.9 首次启用被拒（2026-11-07 17:30 实机）与处置

游戏给出的拒绝单：

```
Mod: DeepSpace Bridge（AI 玩家桥接） (deepspace.bridge), version 3.0.0
Reason: 使用了清单文件中未声明的权限：- 通过映射访问系统和引擎的内部实现
Undeclared capabilities: reflection-external
Scanner findings:
  reflection-external: BridgeApi.HandleAction -> Type.GetField on a computed type   ×2
  reflection-external: GameAccess.FindField -> Type.GetField on a computed type
  network: BridgeServer..ctor/.Start/.Stop/AcceptLoop/HandleClient                 ×5
```

**判定**：这不是代码 bug，是清单申明不全。`ModCapability.Undeclared(detected, declared)`
要求"扫描到的能力必须被 manifest 覆盖"，而 `reflection-external` 确实在用
（正式版私有化的那几个成员只能反射读）。处置：在 manifest 补
`<Capability>reflection-external</Capability>`，同时**去掉**原先保守多申明的 `files`
——扫描结果里没有它，多申明会让启用提示写出不实的权限。

**顺带排掉的一个坑**：拒绝单抬头写 `Game: VERSION 100-Rev12`，但版本门禁
（`ModUIManager.VersionMatchesGame`）比的是 Unity 的 `Application.version`：
- `globalgamemanagers` 里的 `bundleVersion` = **`0.46D`** → 归一化 `0.46`；
- `100-Rev12` 只是 `PlayerStore.VERSION_NUMBER` 常量（`ModRefusalUI.cs:58` 把它写死在拒绝单抬头）。

所以 `<GameVersions>` 必须保持 `0.46D`；若照抄界面上的 `100-Rev12`，归一化后是 `100`，
反而与 `0.46` 不匹配，会多出一条"版本不符"提示。

**状态**：manifest 已更新为 v3.0.1、`Capabilities = network, reflection-external`，
已重新部署。版本哈希变化，需在游戏内再次确认启用。

### 5.2 发现的问题

#### P1（真实 bug，已定位根因）`stow_loot` 把两件物品叠进同一格

- **现象**：地面 2 件（碳酸代乳、垃圾）→ `stow_loot` 返回
  `"拾荒收纳：2 件装进背包/口袋，失败 0 件"`，但 `/debug/slots` 只有
  `pocketLeft=1（垃圾）`；**用户实机观察：两件物品叠在同一个格子里**。
- **根因**（用户观察确认）：正式版 `GameGridInventory.UncheckedAccept()` 只做
  `items.Add(item)` + `item.ValidateShapeState()`，**完全不检查目标格是否已被占用**。
  物品位置由 `modifiedXOrigin/modifiedYOrigin` 决定，从「地面」搬过来的物品原点还停在原格子，
  第二件物品的原点与第一件相同 → 两件叠在同一格，后写入的顶掉前一格的引用，
  `childItems` 里就只剩一件（看上去像"消失"）。
- **修复**（`TryPlaceInto`，已编译）：
  1. 遍历目标格子的每个坐标，把物品原点移过去；
  2. `ValidateShapeState()` 重建 `modifiedShape`（形状用的是绝对坐标，必须跟着原点重建）；
  3. 用游戏自己的 `CheckShapePlacement(item, shape, 空列表)` 校验——越界与重叠都在里面；
  4. 通过才 `UncheckedAccept`，并通过 `ContainsItem` 按引用复核确实入库；
  5. 三个槽位都放不下 → 用同样方式把物品**放回地面空位**，不再原地丢失。
  - 返回串附逐件去向：`「垃圾」→左口袋 「碳酸代乳」未落位`。
  - 注意 `CheckShapePlacement` 内部会 `ignoredItems.Contains(o)`，**传 null 会 NRE**，必须传空列表。
- **未部署**：游戏运行中 DLL 被映射锁定（`WinError 1224`），需完全退出游戏后执行
  `scripts/deploy_mod.py`。

#### P2（非迁移引入）`run --event-driven` 会长时间无输出

- 现象：`run --max-steps 6 --live --no-mouse --source bridge --event-driven` 挂起 6 分钟无任何步骤输出。
- 对照：同样的 `run` 去掉 `--event-driven`，3 步连续正常完成。
- 判断：事件驱动在"状态无变化"（谈判面板静态停留）时等待，且没等到心跳兜底。
  与 mod 无关，属 Python 侧既有行为，但会让人误以为桥死了。建议后续调 `event_idle_limit`。

### 5.4 P1 的最终处置

第一版只做了"落位校验 + 放回地面"，属于兜底。用户实机观察到**两件物品叠在同一格**后，
根因才定位到 `UncheckedAccept` 不做占用检查（详见 5.2 P1）。

现在改为 `TryPlaceInto`：找空位 → 改原点 → `ValidateShapeState` 重建形状 →
`CheckShapePlacement` 校验 → 入库 → 引用复核；放不下就回地面空位。
