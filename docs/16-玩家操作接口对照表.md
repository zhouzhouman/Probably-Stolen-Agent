# 玩家操作接口对照表（v2.6）

> 本文回答一个问题：**知识库里每条机制，AI 靠什么「玩家动作」去执行？**
> 每一项都写明：接口 → 对应的玩家操作 → 触发条件 → 生效链路 → 失败语义。
>
> 硬约束（用户 2026-10-25 指令）：
> 1. 只允许**玩家视角的合法交互**（点击、拖拽、对话、交易、使用）；
> 2. **禁止**直接改变量、调内部方法、绕过校验来凭空生成物品/资源/状态；
> 3. 不引入重复物品、状态错乱。
>
> 因此本表把接口分成三级，并如实标注：**UI 级** > **库存 API 级** > **字段级**。
> 字段级只有历史遗留的两处，且都不生成物品（见第六节「待迁移」）。

## 〇、v2.6 增补：节点坐标层与拖拽派发

### `GET /ui/nodes` — 自绘 UI 的几何清单

自绘界面的渲染节点是 `TreeNodeRender`（它实现 `IBeginDragHandler / IDragHandler /
IEndDragHandler / IDropHandler / IPointerClickHandler`——**物品拖拽和点击全由它处理**）。
本端点列出每个活跃节点的屏幕矩形：`{cx, cy, w, h, elem, id, name, count, go, path, text}`。

实测（Day 75 店内）：6736 个节点中 495 活跃、240 有合理尺寸（2~1200px）。
坐标已验证落在合理屏幕位置（如 `(1840,506) 160x160`）。

**工程坑（已修复）**：`GetWorldCorners(Vector3[])` 传托管数组不会被回填（宽高全 0），
必须传 `Il2CppStructArray<Vector3>`；游戏的 canvas 自带大 scaleFactor，宽高不能拿
`rect × scaleFactor` 估，只能信 `WorldToScreenPoint`。

### `ui_drag {from_x, from_y, to_x, to_y}` — 完整拖拽

派发序列：`pointerDown → initializePotentialDrag → beginDrag → drag×8 → drop（落点控件自己判定收不收）→ endDrag → pointerUp`。
交不交换由游戏的 `IDropHandler` 算，脚本不做任何回滚——被拒时游戏自己放回原格。

### 当前限制（如实）

`TreeNodeRender.element`（指回 PixelElement）在当前存档的**所有活跃节点上均为 null**：
- 240 个常驻节点是卷帘门/电话/文本这类固定 UI；
- **物品画在世界层（店景 sprite），不是 UI 节点**，因此「某件物品在屏幕哪里」仍需视觉定位；
- 结果：`ui_drag` 能力已就绪且走合法链路，但**给不了物品级目标坐标**；
  机器装料/取产与上桌暂维持 v2.5 分类（库存 API 级 / 字段级）。

## 一、本轮新增（v2.5）

### 1. `ui_hit {x, y}` — 这一点上有什么 UI（只读）

| 项 | 内容 |
|---|---|
| 玩家操作 | 鼠标悬停（不点击） |
| 触发条件 | 场景里有 `EventSystem`；坐标是 Unity 屏幕坐标（原点左下，1920×1080） |
| 生效链路 | `EventSystem.RaycastAll` → 返回命中对象名与层级路径（最多 12 层） |
| 失败语义 | 坐标非数值 → 直接报错；无命中 → `hits: []`（不是错误） |
| 用途 | 自绘界面的**定位**手段：先探明某点归哪个对象管，再决定点不点 |

### 2. `ui_click {x, y, button?, double?}` — 玩家点击那一点

| 项 | 内容 |
|---|---|
| 玩家操作 | 鼠标左键 / 右键 / 双击 |
| 触发条件 | 该点必须命中 UI 对象；`EventSystem` 存在 |
| 生效链路 | `RaycastAll` → 对命中对象派发 `pointerDown → pointerUp → pointerClick`（与玩家点击同一条 Unity 事件管线，命中对象的 `OnPointerClick` 内全部校验照常执行） |
| 失败语义 | 无命中 → `该位置没有可点击的 UI 对象`；命中但无处理器 → 事件被丢弃（无状态变化） |
| 为什么需要它 | 平板电脑、网络商店、机器窗口都是 **PixelWindow 自绘**：没有 Button 组件，`click_button` 找不到。这类界面只认坐标 |

### 3. `object_action {type?, name?, text?, path?, op?}` — 对具名对象做点击 / 双击 / 右键

| 项 | 内容 |
|---|---|
| 玩家操作 | 点击 / 双击 / 右键 |
| 触发条件 | 至少给一个定位字段（type / name / text=工具提示 / path 子串）；对象必须 `activeInHierarchy` |
| 生效链路 | 按 `IClickable.OnClick()` / `IDoubleClickable.OnDoubleClick()` / `IControlable.OnRightClick()` 调用——**就是玩家点击时游戏自己调的那三个方法** |
| 失败语义 | 找不到 → 列出收到的定位条件；对象不支持该操作 → 列出它支持哪几种 |
| 与 `click_button` 的关系 | `click_button` 仍优先走 uGUI Button / 26 类白名单；找不到时**自动兜底**到全量可点击对象，并支持 `op` 参数 |

### 4. `GET /ui/objects` — 全量可点击对象清单

| 项 | 内容 |
|---|---|
| 玩家操作 | 无（读取可用交互点） |
| 内容 | 每个对象的 `type / name / text(工具提示) / path / click / double_click / right_click` |
| 覆盖 | 从固定 26 类白名单改为**扫描所有 MonoBehaviour 按接口识别**；当前场景实测 16 个 |
| 限制 | 自绘的**像素级条目**（平板内页、网络商店列表）不产生独立对象，这里列不出来——它们只能靠 `ui_hit`/`ui_click` 按坐标操作 |

### 5. `dialog_choose {text}` — 按选项文字选（新增，优先于序号）

| 项 | 内容 |
|---|---|
| 玩家操作 | 点击对话选项气泡 |
| 触发条件 | `dialog.is_choice=true`；给出 `text` 时按**包含匹配**（先精确、再子串），命中多条取第一条 |
| 生效链路 | 读 `DialogUIManager.dialogChoiceBubbles` 的可见气泡文本 → `SelectChoice(bubble.index)` |
| 失败语义 | 无匹配 → 报错并**列出当前全部选项文本**（AI 可据此重选，不用猜） |
| 为什么改 | r75 事故：盲选 `index 0` 进了「延期交租」分支，房东 `business_complete` 永远 false、不可遣散、整局死锁。按文字选把「看到什么点什么」写进接口 |

### 6. `GET /expedition` + `expedition_send` / `hire_worker` — 远征与雇工（带门禁）

| 项 | 内容 |
|---|---|
| 玩家操作 | 夜间在「雇工/远征」面板选地点 + 选雇工 → 派遣 |
| 只读状态 | `/expedition` 返回 `unlocked / hirelings[] / locations[]{id,name,danger,traffic,legality,unlocked} / ongoing` |
| 触发条件（派遣） | ① `isExpeditionUnlocked=true`；② 至少 1 名雇工；③ 地点已解锁 |
| 当前实测 | 本存档 `unlocked=false`、`hirelings=[]`、`dumping_grounds` 地点已解锁 |
| 失败语义 | 未解锁 → `远征未解锁（isExpeditionUnlocked=false）……本动作不改变任何状态`；无雇工 → `先招募雇工` |
| 为什么不做「能跑就跑」 | `ExpeditionData.CreateExpedition` / `Hireling.Hire` 是内部方法，绕过面板校验。按用户约束**明确拒绝**，而不是偷偷调用 |

## 三、触发条件速查：AI 每步该看哪个字段

| 要做的判断 | 看这里 |
|---|---|
| 能不能卖 | `visible_info.sellable_now`（v2.4 起由游戏 `IsClientBuyingThisItem` 判定，不是标签猜的） |
| 能不能买 | `visible_info.client.is_selling` + `inventory.not_owned` |
| 能不能打烊 | `store_state=OPEN` + 队列；有顾客会自动确认 |
| 能不能外出 | `night.visit_left>0` + `night.is_outside` |
| 能不能拾荒 | `night.scavenging_attempts>0` + 当前地点 |
| 机器里有什么 | `visible_info.machines`（只列有内容的槽） |
| 能不能远征 | `/expedition.unlocked`（false 时一律不要尝试） |
| 对话怎么选 | `dialog.choices[].text` → `dialog_choose {text}` |

## 四、本轮明确「不做」的部分及原因

| 机制 | 玩家操作 | 为什么没做成接口 |
|---|---|---|
| 远征派遣 | 面板选点 + 选雇工 | 存档 `isExpeditionUnlocked=false`；且面板为自绘，无组件可枚举。已提供门禁拒绝，避免 AI 幻觉 |
| 雇工招募 | 面板招募 | 同上（`hirelings=[]`） |
| 许可购买（枪证/网络升级） | 网络面板点条目 | 面板自绘，条目无独立对象；需先用 `ui_hit` 找到坐标才能点 |
| 议价四方向（让利/争利） | 谈判面板按钮 | 同上：面板只有 CloseButton/WindowButton 是 uGUI，方向键是自绘 |
| 彩票买号 | 与代表对话选号 | 代表只在周六出现；接口 `dialog_choose {text}` 已就绪，等 NPC 到场即可用 |
| 治疗/戒瘾 | 夜间服务 / 医生对话 | 服务未解锁时为非法；`night_service` 已能选已解锁项 |
| 屠宰取肉（鱼→鱼片） | 用刀屠宰 | 仓库无刀具；屠宰是 UI 动作，未找到可调用的界面入口 |
| 拖拽（物品在容器间移动） | 按住→拖→松手 | `ui_drag` 已实现走 IDropHandler 链路，但物品节点不在 UI 层（`element` 全 null），给不出物品坐标；需视觉定位 |

**统一原则**：宁可返回「未解锁 / 做不到」并说明条件，也不调用内部方法伪造结果。

## 五、如何验证一个界面能不能自动化

```bash
# 1) 先看有没有组件级对象
curl/GET /ui/objects

# 2) 没有的话，用射线探坐标（Unity 屏幕坐标，原点左下）
POST /action {"action":"ui_hit","x":1200,"y":540}

# 3) 命中后再点
POST /action {"action":"ui_click","x":1200,"y":540}
```

实测样例（Day 75 店内）：`ui_hit(1760,240)` → `SleepingBag`；`ui_hit(320,240)` → `_AdvCalendar`；
`/ui/objects` 返回 16 个具名可点击对象。

## 六、待迁移：两处非 UI 级实现（如实标注）

| 接口 | 现状 | 风险 | 迁移方向 |
|---|---|---|---|
| `place_item` | 直接写 `PlayerStore.currentNegociatedItem` 与 `NegociationUIManager.currentNegociatedItem`（v0.5.0「纯变量路线」） | **不移动物品网格**，只标记议价对象；画面桌上没东西 | 改为 `ui_click` 双击/Ctrl+点击物品格 → 走游戏自己的上桌逻辑 |
| `machine_put` / `machine_take` | 调 `GameInventory.Expel` / `UncheckedAccept` 在真实容器间搬运 | 走的是容器自身的接受校验（不接受会放回），**不生成物品**；但绕过了拖拽手势 | 改为 `ui_click` 在机器窗口内拖拽（需机器窗口坐标） |

这两处都不创建物品、不修改现金，且都带事后校验（`/state` 差分）；在自绘界面坐标化之前保留，作为兼容路径。
