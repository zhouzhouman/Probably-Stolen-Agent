### B1 `click_button` 的 path/type 被丢弃

```python
# 修复前
"click_button": {"name", "text"},
params = {k: v for k, v in raw_params.items() if k in allowed}   # path 在这里被丢掉
```

模型按提示词输出 `{"name": "CloseButton", "path": "_AdvCalendar"}`，到达桥接时只剩 `name`。
桥接的 `FindButton(name, text, pathContains)` 本来支持 path，两个面板各有一个 `CloseButton` 时就会点错。

修复：白名单补 `path` / `type`，校验时去空白并保留；「至少其一」的判定与桥接 `HandleAction` 对齐。

### B2 夜晚白名单漏掉拾荒链路（最影响「赚钱」的一条）

| 动作 | 修复前 brain 白名单 | 修复前 agent_loop 白名单 |
|---|---|---|
| `equip_backpack` | ❌ | ❌ |
| `take_ground_items` | ❌ | ✅ |
| `stow_loot` | ❌ | ✅ |

`decide()` 在夜晚阶段按 `NIGHT_PHASE_ACTIONS` 硬过滤 `extra_actions`——**模型即使想装背包、想收纳，
也会被校验层以「动作不在白名单」拒绝**。而提示词里写着「出门前先 equip_backpack」「离场前必须 stow_loot」。
两份白名单现已同源，并加了一致性测试：`NIGHT_PHASE_ACTIONS <= agent_loop._NIGHT_PHASE_ACTIONS`。

### B3 真实运行路径上守卫全部失效

`cli run` 调用 `run_loop(config, ...)` 时不传 `bridge_client`。于是：

- `_morning_report_guard(None)` → 直接返回 None，晨报面板守卫**永不触发**；
- `run_loop` 每步的 `_live_store_state(None)` → None，昼夜阶段校正失效；
- `_fallback_action(..., None)` → 读不到 `store_state`，只能退回旧兜底。

之前所有相关测试都显式注入假客户端，所以测试全绿、线上却静默降级。修复：`step_once` / `run_loop`
在 `bridge` 通道下按需构造客户端并全程复用（构造不发请求，无副作用）。

## 三、十日净赚 1000 元：目标拆解

### 3.1 目标定义（写进 AI 的每一步提示词）

| 项 | 定义 |
|---|---|
| **主 KPI** | 10 个经营日内，**现金净增 ≥ 1,000 元**（期末现金 − 期初现金） |
| 期初锚点 | 现金 **14,100**；库存估值 **37,383**；资产合计 51,483 |
| 达成线 | 期末现金 ≥ **15,100** |
| 硬约束 1 | 现金始终 ≥ `rent_due` × 3（当前租金 321，红线 ≈ 963） |
| 硬约束 2 | 期末库存估值 ≥ 期初的 **70%**（≥ 26,168）——卖货变现可以，清仓刷分不行 |
| 硬约束 3 | 产能设备（MACHINE/STORAGE/养殖/机器区/能量阵列）一律不卖 |
| 计时 | 优先用 `/state.day`；旧插件无 day 时按「清晨次数」计 |

> 为什么用现金而不是「现金+库存」：库存估值是游戏自己估的零售价，用它记账会把没卖出去的货
> 提前算成利润（囤货刷分）。现金净增是玩家语境里「赚了多少钱」的直白含义；库存只作为余额底线。

### 3.2 数学拆解

```
目标：10 天 +1,000 现金  →  日均 +100

成本（10 天，按当前服务设置实测）：
  房租      321（4 天后）+ 约 333（下一期）              ≈  654
  夜间服务  已勾选 SEC_INFORMANT 10 + 买家推荐 10
            + 卖家推荐 10 + WILD_FIXER 25 = 55/晚 × 10   =  550
  合计成本                                                ≈ 1,204
需要的销售回款：1,000 + 1,204 ≈ 2,204  →  日均 ≈ 220

若关掉不必要服务（只留保险 3 晚 + 偶发支出）：
  成本 ≈ 654 + 300 = 954    →  回款需求 ≈ 1,954（日均 195）
```

这 55/晚是**实盘读 `/state.services` 才发现的**：四个 `is_using=true` 的小额服务加起来
几乎等于半个利润目标。所以计划里加了一条硬动作：**每天进夜晚面板先关不必要的服务**
（垃圾=0 关清洁、无犯罪点关 WILD_FIXER、客流正常关推荐类），这一步本身就值 250~550。

即便只发挥 50%（日均成交 2 单、回款 120），10 天也能净增 ~1,200 − 1,204 ≈ 0 —— **不达标**。
所以关键不是「有没有客人」，而是**别把买家放走、别把服务费漏掉**：
最大的两个漏损是「顾客在买、库存有货，却 dismiss」与「55/晚的默认服务」。
B6 的库存聚合 + `sellable_now`、v2.2 的服务关停规则，正是为这两件事服务的。

### 3.3 十天节奏（阶段目标）

| 阶段 | 天数 | 目标 | 打法 |
|---|---|---|---|
| S1 变现启动 | D1–D2 | 现金 +300 | 先卖高值滞销品：高级滤水器、模组、注射器、努特加；`display_case` 放 1~2 件引流；不进货 |
| S2 稳定经营 | D3–D6 | 累计 +600 | 买家优先：`sellable_now` 非空就 `sell_item`；卖家用 JUNK 直接 dismiss；鱼片/食品按日出货 |
| S3 交租+冲量 | D7–D8 | 累计 +900 | 交租日前只卖不买；商人到场清库存回血；现金 ≥ rent_due 再 `pay_rent` |
| S4 收尾盘点 | D9–D10 | ≥ +1,000 | 补齐差额（卖高值品），核对库存底线 ≥ 70%，`save_game` 存档 |

### 3.4 每日标准作业（SOP）

1. **晨间（MORNING）**：看到日历/夜间报告面板 → 立即 `click_button {"name":"CloseButton","path":"_AdvCalendar"}`；
   `open_shutter` 开张；`alway_call` 打开自动迎宾。
2. **接待**：`call_next` → 看 `client.is_buying / is_selling`：
   - 买家：`sellable_now` 非空 → `sell_item`（identifier 照抄）；空 → `dismiss_client`，**不要反复试**；
   - 卖家：物品含 `JUNK` → dismiss；非 JUNK 且现金 ≥ rent_due×3 → 低吸；否则 dismiss；
   - 特殊 NPC（`dismissable=false`、盘查员/房东）→ 走完对话，别 `dialog_advance` 已结束的对话。
3. **批发**：`nego_buttons.wholesale=true` → `click_button AcceptWholesale`；成交后系统自动 `transferButton` 收纳。
4. **打烊前**：`queue.can_next=false` 且店内无人 → `end_day`；夜间只做夜晚动作。
5. **夜晚**：`night_services` → 只勾保险（库存 > 1 万时）/清洁 → `end_day_confirm`；
   有 `visit_left` 且未重伤 → `equip_backpack` → `open_map` → `go_out scavenging` → `scavenge`×N →
   `stow_loot` → `leave_outside`。
6. **服务费**：进夜晚面板先关不必要服务（WILD_FIXER / SEC_INFORMANT / 推荐类，55/晚），只留保险与真正需要的项。
7. **收尾**：`save_game`，跑一次 `python -m game_agent.cli goal` 记账。

### 3.5 批次执行手册（可直接照做）

```bash
# 0. 启动游戏（加载 v2.1.0 插件），确认 day 字段
python -m game_agent.cli bridge state | grep '"day"'
python -m game_agent.cli goal                 # 应显示 第 N 天 / 周期第 1/10 天

# 1. 每批 40 步，禁鼠标（只用游戏 API 直调）
python -m game_agent.cli run --source bridge --live --no-mouse \
    --max-steps 40 --event-driven

# 2. 每批结束：看进度 + 存档
python -m game_agent.cli goal
python -m game_agent.cli bridge action save_game

# 3. 中止：创建 STOP 文件（下一步前退出）
type nul > artifacts\STOP
```

批次安排：D1–D2 一批（约 25 步）、D3–D6 两批（各 40 步）、D7–D10 两批（各 40 步）。
每批前确认 `artifacts/STOP` 不存在；每批后核对：

| 检查项 | 通过标准 | 不通过的处理 |
|---|---|---|
| 天数推进 | 每批推进 1~3 天，无跳天 | 查 `store_state` 与夜晚白名单；有跳天立即 `load` 最近存档 |
| 现金 | 单调向好（允许进货日回落） | 连续 2 天负增长 → 停止进货，只卖 |
| 租金 | `rent_due` 未滚大、`day_until_rent` 正常递减 | 交租日现金不足 → 商人窗口清库存 |
| 库存 | 估值 ≥ 26,168 | 低于底线 → 停止变现，先补货 |
| 错误率 | < 15% | 连续 3 次业务失败 → 看 steps 里的 detail |

### 3.6 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 收租对话选错（延期） | 中 | 高：欠款滚大、房东卡店 | 只选含「交/付/租金」的选项；现金 < rent_due 时先卖货；异常读档（读档清空顾客） |

| 夜间服务吃掉利润 | 中 | 每天 −96 | 保险只在库存 > 1 万时买；推荐类服务（10/晚）客流低时不买 |

| 插件未重启 | 中 | 无 day、调试接口不可用 | 批次 0 先验证 `bridge state` 有 `day` |
