# 十天连续游玩可行性评估（2026-10-19 深夜）

## 一、结论

**当前版本「可以」连续游玩 10 天，但属于「有条件可行」**：

- 昼夜循环、夜晚服务、睡觉换日、次日开张的完整链路已经连续验证通过；
- 单批次（40 步）可无人工干预连续推进 **3 天**（r76），现金 276 → 715；
- 10 天约需 **100~150 步 / 1~1.5 小时**，建议分 3~4 批（每批 40 步）续跑；
- **剩余最大不确定项是「收租日的对话分支」**：选项文本已经暴露给模型，但尚未在真机
  收租对话里验证过「选对交租选项」；选错会进入「延期」分支并让房东卡店（可读档恢复）。

## 五、10 天回归测试方案（建议执行）

1. 每批 `--max-steps 40`，共 3~4 批；每批结束 `save_game`；
2. 每批检查：`day_until_rent` 递减与归零、现金不低于租金、错误率 < 15%；
3. 收租日专项：观察 `dialog.choices` 是否含「交租」文本，模型是否选对；
   若再次进入「延期」分支，立即读档（客户是瞬时状态，读档即清空）；
4. 出现 3 次以上连续业务失败时熔断（已有 MAX_CONSECUTIVE_ERRORS）。

## 六、尚未解决 / 已知限制

1. `pay_rent` 的 `CanPayRent()` 在收租日恒为 false（现金充足、dur=0 时也一样）；
   实际租约变化由房东对话选项触发。**交租的正确选项尚未确认**（r75 盲选 index 0
   进入了「现金未扣、租约重置、房东卡店」的异常分支）。
2. 模型（tokeness/free）仍偶发选择夜晚禁用动作（open_shutter），靠白名单兜底。
3. 单步延迟波动大（15~120 秒），10 天总时长可能超 2 小时。
4. 商店没有「自动买保险/清洁」的策略验证，夜间服务选择依赖模型判断。

- 错误全部为模型层（夜晚误选 open_shutter、JSON 截断、白名单拒绝），自动恢复

  本轮后续未再出现卡店

### 本轮暴露并修复的问题

1. **收租真相**：`CanPayRent()` 用的是 `temporaryRent`（累计欠款），不是名义 `rent_value`。
   上次「延期」把 231 滚成了 693——现金 442 时房东只给「拒付租金」选项。
   已把 `rent_due` / `can_pay_rent` 暴露到 `/state`，红线与提示词都改用真实应缴。
2. **卡店 NPC 自愈**：新增 `force_dismiss`（恢复专用，不进模型白名单）+ 连续 5 步检测
   「不可遣散 + 对话已结束」的驻店顾客 → 自动清走，避免整批卡死。
3. **对话选项文本暴露**：模型按文本选（实测「接收5桶」），不再盲选序号。

### 经济结论（重要）

流程「流畅」但**经营是失败的**：现金 715 → 180，租金欠款 693，租约只剩 1 天。
延期分支把债务滚大后，AI 的卖货能力跟不上（大量顾客是卖家/无可卖品类），
形成现金螺旋。若要 10 天「既流畅又健康」，下一步需要强化经营策略：
- 批发采购要按「预计可卖出品类」筛选，而不是看到批发就接；
- 现金低于 rent_due 时只卖不买（v1.5b 已上线，本轮后段生效）；
- 优先服务买家、提高客单价，而不是连续 dismiss。
