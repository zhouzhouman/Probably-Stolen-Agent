# 深空当铺 AI · 数据直读方案（替代视觉识别）

> **文档性质**：技术方案 —— 用「直接读取游戏底层数据」替代「截图 + 视觉大模型识别」
> **动机**：当前视觉管线单步耗时约 7~13 秒（截图 + 视觉模型 + 决策模型），延迟过高
> **结论（实测验证）**：该游戏提供 **明文日志流 + 明文 JSON 存档** 两个数据源，可完全绕开视觉模型，感知延迟降至毫秒~秒级

## 2. 三个数据源（按可用性排序）

### 2.1 【数据源 A】运行日志流 GameLog_*.txt —— 实时事件流

- 位置：持久化目录，**每次启动游戏新建一个文件**（`GameLog_2026-10-13_22-00-28.txt`）
- 格式：逐行文本，`[HH:MM:SS] [Log|Warning] 消息`，事件发生时即时写入
- 实测包含的关键事件（节选）：

```
[09:19:10] [Log] Arriving                     ← 顾客接近
[09:19:12] [Log] Client Arrived               ← 顾客到达
[09:19:12] [Log] wanted2 SELL                 ← 顾客类型 + 意图（wanted2 通缉犯 / SELL 出售）
[09:19:17] [Log] Conversation Ended!          ← 对话结束
[09:19:44] [Log] Start Action Executed!       ← 动作执行
[09:19:44] [Log] Business Not Done            ← 交易未成交
[09:19:48] [Log] Correct Report of Wanted Customers   ← 举报通缉犯成功
[09:21:44] [Log] Game Saved in Slot: 15       ← 自动保存（每 2~4 分钟一次）
[09:18:36] [Log] tracked price: 101           ← 价格跟踪
```

- **价值**：毫秒级实时的「发生了什么」，天然的事件驱动信号源
- 局限：是事件流而非全量状态（金钱、库存明细要看存档）

### 2.2 【数据源 B】存档 save_*.es3 —— 完整状态快照（明文 JSON！）

- 位置：持久化目录 `save_N.es3`（多槽位）+ `SaveFile.es3`（设置）+ `saves_index.es3`（索引）
- 格式：**Easy Save 3 的明文 JSON**，包含游戏对象的完整序列化树
- 实测结构（`save_16.es3`，75KB 小存档；大存档 1~2MB）：

```
顶层：{ "playerStore": {...}, "storeStation": {...} }
playerStore（144 个字段）关键字段：
  playerCash            = 550        # 现金
  dayUntilRent / rentValue          # 租金倒计时
  dayUntilLoan / loanValue          # 贷款
  storeReputations[]                # 阵营声望（含解锁条件、阈值）
  storeClientManager / storeClientData   # 顾客系统（含通缉、检查、盗窃记录）
  nightLogs / dialogHistory          # 夜间结算日志、对话历史
  mainInvJSON / backInvJSON / showcaseInvJSON / soldInvJSON / trashcanInvJSON ...  # 11 个库存（嵌套 JSON 字符串）
  PhoneClientDict                    # 电话客户表
storeStation：order / traffic / happiness / dayCounter / ...
```

- 库存物品实测样例（`mainInvJSON` 解析后）：

```json
{"identifier": "save_bag", "unitCount": 1, "uuid": 0,
 "itemShape": {...}, "itemType": "GameItemElement", "name": "“泥炭”合成肉",
 "unitValue": 25, ...}
```

- **价值**：单位「元」级的完整状态——现金、库存每件物品、顾客、声望、历史
- 更新时机：自动保存每 2~4 分钟 + 关键节点（对话结束/场景切换）触发
- ⚠️ 存档有两处「非标准 JSON」，需要宽容解析器（已实现，见 §4）：
  1. 数字做键：`{"PhoneClientDict":{8376:{...}}}` （JSON 标准要求键是字符串）
  2. 中文全角引号被转义：`\“泥炭\”合成肉`（`\“` 不是合法 JSON 转义）

### 2.3 【数据源 C】BepInEx IL2CPP 注入（可选终极方案，未实测）

- 原理：向 IL2CPP 游戏注入 BepInEx 6 插件，用 C# / Il2CppInterop 直接读写内存中的游戏对象（`PlayerStore`、`StoreStation`、顾客 `Client`……）
- 能力上限最高：**每帧级实时状态 + 直接调用游戏方法**（如直接执行"收购/还价/鉴定"，完全绕开鼠标键盘）
- 前提：游戏自带 ModLoader 但试玩版禁用不影响 BepInEx（独立注入）；需实测注入兼容性
- 成本：需要 C# 插件开发 + IL2CPP dump（类/方法签名）；游戏更新后需适配
- 决策：**先不做**，作为 A+B 满足不了需求时的升级项。

## 3. 方案对比

| 方案 | 感知延迟 | 信息量 | 侵入性 | 开发成本 | 备注 |
|---|---|---|---|---|---|
| 现状：截图+视觉模型 | 3~6s/次 | 中等（模型解读有误差） | 无 | 已投入 | 当前延迟瓶颈 |
| **A：日志流监听** | **<10ms** | 事件流 | 无 | 低 | 实时性最好的免费午餐 |
| **B：存档解析** | **~100ms**（含 JSON 解析） | **完整状态**（比视觉更丰富精确） | 无（只读） | 低 | 更新取决于保存时机 |
| C：BepInEx 注入 | <1ms | 全量内存对象 | 注入游戏进程 | 高 | 终极；控制层可免鼠标 |

**推荐：A + B 组合**。日志给「何时决策」，存档给「当前全貌」，两者结合即可完全替代视觉观察。控制层继续复用已验证的鼠标/键盘模块（±1px 精度），仅把「观察输入」换掉。

## 4. 推荐架构（观察层替换）

```
旧管线（7~13s/步）：
  capture(PNG) → 视觉模型(图片) → brain(文本) → control(鼠标键盘)

新管线（感知 <100ms）：
  ┌─ LogTail ──→ 事件流（毫秒级）──┐
  │                                ├→ StateBuilder（结构化状态 JSON）→ brain → control
  └─ SaveWatch → 状态快照（分钟级）─┘
```

设计要点：

1. **新模块 `game_agent/statewatch/`**（暂命名）：
   - `log_tail.py`：定位最新 GameLog（自动跟随新文件）→ 增量读取 → 正则解析为结构化事件
   - `save_watch.py`：监听 `save_*.es3` 变化（mtime/大小）→ 宽容解析 → 提取状态
   - `state.py`：合并「事件流 + 快照」→ 统一 State 对象（现金 / 库存 / 当前顾客 / 时间线）
2. **宽容 JSON 解析器**（已参考实现）：

```python
def lenient_fix(s: str) -> str:
    s = re.sub(r'([{,])(\d+):', r'\1"\2":', s)          # 数字键补引号
    for _ in range(10):                                   # 循环清理非法转义
        new = re.sub(r'\\(?![\\"/bfnrtu])', '', s)
        if new == s: break
        s = new
    return s
```

3. **CLI**：`python -m game_agent.cli watch`（实时打印状态变化）/ `watch --once`（单次快照，供调试）
4. **离线可测**：历史日志 + 存档全部保留在本地 → 单元测试与回放**无需启动游戏**（确定性好于视觉方案）
5. **brain 不变**：prompt 从「看图找按钮」改为「读状态 JSON 决策」，token 用量同时下降

## 5. 关于「控制」的路线

| 层 | 方式 | 状态 |
|---|---|---|
| 控制-1 | 现有鼠标/键盘控制（数据驱动，不再依赖视觉找坐标） | 已有，直接复用 |
| 控制-2 | 存档写回实验（改现金/改物品） | ⚠️ 有被游戏内存覆盖的风险，仅作实验，不建议做主控制 |
| 控制-3 | BepInEx 直调游戏方法（免鼠标、零延迟） | 数据源 C 一并评估 |

## 6. 分阶段实施计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1（建议先做）** | `statewatch` 模块：日志 tail + 存档解析 + State 组装 + CLI | 用历史日志/存档离线回放出完整状态；游戏运行时实时跟随 |
| P2 | brain 输入切换为结构化状态（保留视觉为兜底） | 结构化输入下完成一次完整「观察→决策→控制」 |
| P3（可选） | BepInEx 注入评估（对 demo 实测注入兼容性） | 能读到内存中实时对象 |

## 7. 风险与注意事项

1. **存档解析的健壮性**：游戏版本更新可能改变字段；用「缺字段容错 + 事件流为主」的思路降低耦合
2. **写存档危险**：游戏存档在退出/自动保存时会整体重写，外部修改可能被覆盖甚至损坏存档 → 只读优先，备份后实验
3. **日志跟随**：每次启动生成新文件，监听器需按「最新创建」切换；旧文件不删除可直接用于回放
4. **合规**：均为本机单机游戏的本地数据读取，无内存注入（P1/P2），风险最低
