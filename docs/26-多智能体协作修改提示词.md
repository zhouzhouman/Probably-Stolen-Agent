## 0. 使用说明与两套架构的区分

**先分清两套「多智能体」**，不要混淆：

| | 游玩时的多智能体（项目既有，用户 2026-10-15 定义） | 修改代码时的多智能体（本文新增） |
|---|---|---|
| 角色 | 主 Agent + 感知 perception / 机制知识库 knowledge / 行动规划 planning / 接口校验 validation | 总控 + 契约 / 平台 / 桥接 / 观察 / 知识 / 策略 / QA |
| 顺序 | 感知 → 知识库 → 规划 → 校验 → 执行 → 重新感知，**严格不可跳步** | 见本文 §2 的阶段 DAG |
| 硬约束 | 每轮一个原子动作；未解锁禁止行动；弹窗未关禁止下一天；禁止跳天；主 Agent 禁止直接调游戏接口 | 见本文 §3 的共享规约 |

**本文的所有产出，最终都不得破坏左侧那套严格顺序与硬守卫**（`docs/24` §1.4 列出的守卫是必须保留的资产）。

### 怎么用这份文档

1. 把 §1 的「总控提示词」整段复制给主 Agent（或作为本次改造的系统提示）。
2. 按 §2 的阶段顺序，把 §4 的任务卡**整段复制**给对应子智能体；每张卡自含角色、背景、输入、输出、禁止事项、验证方式，不依赖对话上下文。
3. 每张卡完成后由 QA 按 §5 门禁验收，未通过不得进入下游阶段。
4. 卡内「改动清单」表的每一行都标了优先级与验证方式，可单独派工或裁剪批次。

### 5.3 回滚策略

1. 每张卡的「回滚点」列给出可回退的最小粒度；阶段 0/3 的契约改动必须整卡回滚，不能只回一半（否则白名单又分叉）。
2. `mod/` 侧任何 DLL 覆盖部署前先关闭游戏进程（taskkill），并保留上一版 DLL 为 `.bak-<version>`；`scripts/deploy_mod.py` 已有迁移逻辑，不要绕过。
3. `.env`、`config/agent.json`、`artifacts/`、`knowledge/mechanics/` 在改造开始前做一次快照（复制到 `artifacts/pre_refactor_snapshot/`，不删除既有文件）。
4. 知识卡是**追加标记**（deprecated / gated_until / game_version），不做物理删除，随时可按标记恢复检索。
5. 每完成一个 P0 任务立即跑 V1 + V5；失败即回到该任务开始前的状态，不累积多个未验证改动。

### 5.4 与既有游玩架构的兼容承诺

本改造**不改变**用户 2026-10-15 定义的多智能体游玩架构：
感知 → 知识库 → 规划 → 校验 → 执行 → 重新感知，严格顺序、每轮一个原子动作、执行后重新感知、
主 Agent 禁止直接调用游戏接口、❌非法时禁止执行任何接口并返回失败原因重回规划、
决策日志格式（轮次 ID / 状态摘要 / 待下发任务 / 校验结论 / 下一步动作指令）。
所有新增守卫都挂在既有 `_guard*` 链尾或作为并列守卫，**不替换、不跳过、不 reorder**。
