# 28 · 简历向 MCP 融合方案

> 生成日期 2026-11-17
> 决策问题：本项目要写进简历的 Agent 项目，是否融合创意工坊 mod「游戏 MCP · AI 游玩」（`local.game-mcp` v1.2.7）的技术？怎么融合？
> 结论：**融合协议层与工具契约设计；不融合虚拟输入/Harmony IL 补丁；不抄它的 Skill 知识文档。**

---

## 0. 结论先行

| 项 | 决策 | 一句话理由 |
|---|:--:|---|
| MCP 协议层（JSON-RPC 2.0 / tools-list / tools-call） | ✅ **融合** | "MCP" 是当下 Agent 简历的高识别度关键词，写进 JD 命中率直接提升 |
| 工具契约设计（schema + `readOnlyHint`/`destructiveHint` + 纪律写进 description） | ✅ **融合** | 改动小、面试能讲 10 分钟，体现"Agent 工具安全"的工程判断力 |
| `scene` 陈旧状态守卫 + `Verify` 执行后回读 | ✅ **融合** | 与我们"只认现金 diff"是同一思想，泛化后能形成完整的"执行安全三件套"叙事 |
| `game_ui.openPanels` 模态/控件 ID 设计 | ⭕ **第二阶段融合** | 补我们 UI 交互短板，但属功能补全，不是简历叙事必需 |
| 虚拟输入 + Harmony IL 补丁（106 个 metadata token） | ❌ **不融合** | 锁死 Build、叙事会变乱、讲解成本高，性价比最低 |
| 它的 6 篇 Skill 经营知识 | ❌ **不抄** | 抄了会丢失我们 203 张 trigger 卡的独特性，且是别人的资产 |

**核心思路**：不改我们的"大脑"（多智能体流水线 + 守卫 + 203 卡），只给大脑装一个**标准插座**。简历上从"自研脚本"升级成"具备标准工具协议的 Agent 系统"。

---

## 1. 为什么融合（简历视角的价值）

### 1.1 我们项目现在的三个简历痛点

1. **自研 HTTP 桥 8965 没有行业辨识度**。面试官 30 秒扫简历，看到"HTTP 桥 61 个动作"容易归类成"爬虫/自动化脚本"，而不是 Agent 系统。
2. **README 严重过时**。`README.md:8-21` 还在写 BepInEx、44 个业务动作、状态签名 15/16 字段，而实际是原生 mod、61 个 case、20 字段。**这是简历场景下的硬伤**——面试官对照 README 和代码，信任感直接归零。
3. **多智能体架构是真的，但叙事散落在 `docs/08`**。简历需要一个能一句话讲清的架构图。

### 1.2 融合后的收益

| 简历关键词 | 融合前 | 融合后 |
|---|---|---|
| Multi-Agent / 多智能体流水线 | ✅ 有 | ✅ 保留 |
| **MCP（Model Context Protocol）** | ❌ 无 | ✅ **有** |
| **Tool Schema / 工具契约** | ❌ 弱 | ✅ **强**（单一契约源生成） |
| **Agent 执行安全** | 有但分散 | ✅ 成体系（守卫+陈旧检测+回读） |
| RAG / 知识库检索 | ✅ 203 卡 trigger 检索 | ✅ 保留，可对标"按需知识注入" |
| 工程化 | ✅ 824 测试 / CI | ✅ 保留 |

## 2. 为什么不融合虚拟输入

技术上它很炫（IL 层替换 106 处 `UnityEngine.Input` 调用），但简历场景不划算：

1. **脆弱性会被追问**：它靠 `ModuleVersionId` GUID + 106 个 metadata token 锁死 Build 26525552。面试官一句"游戏更新了怎么办"就能问住——答案是"等作者适配"，这不是加分项。
2. **叙事冲突**：我们的路线是**直调游戏内部 API**（快、一步到位），它是**演一遍玩家操作**（保真、慢）。两条路线混进一个项目，架构图会变成"既直调又模拟"，面试官会质疑设计一致性。
3. **讲解成本**：要讲清 Harmony Transpiler、metadata token、`BaseInput.inputOverride`，至少需要 5 分钟铺陈，而简历面试通常只有 1-2 分钟讲亮点。
4. **我们已有替代方案**：自绘 PixelWindow 没 Button 的问题，用 `game_ui` 的控件 ID 设计就能补（第二阶段），不需要动 IL。

> 唯一例外：如果你要投的是**游戏 Mod 开发 / 逆向工程**岗位，那虚拟输入反而是最强亮点。判断标准看目标岗位。

## 3. 融合路线（三阶段，按简历收益排序）

### 阶段 1 · 最小可行融合（1–2 天，简历必需）

**目标**：在 mod 侧加一层 MCP 协议适配器，**完全复用现有 61 个动作 case 和 `/state` 字段**，不重写业务逻辑。

**架构**：

```
AI 客户端 (Claude / Cursor / WorkBuddy)
    │  MCP / JSON-RPC 2.0 : 28739
    ▼
McpAdapter.cs（新增，协议适配层）
    │  复用 contracts.py 派生的工具 schema
    ├── tools/list  ← 读 mcp_tools.json（由契约源导出）
    ├── tools/call  ──┐
    └────────────────┤
                     ▼
            现有 BridgeApi（127.0.0.1:8965）
                     │  现有 61 个 case + /state
                     ▼
                  游戏进程
```

**最低风险的实现方式**：`McpAdapter` 内部用 `HttpClient` 回调本机的 `127.0.0.1:8965`（回环自调），**一行现有代码都不用改**。多一跳网络开销（本机 <1ms），但简历场景完全可接受。

**具体改动**：

| # | 文件 | 改什么 | 优先级 |
|---|---|---|---|
| 1 | `mod/src/McpAdapter.cs`（新） | 手写 JSON-RPC 2.0：`initialize` / `ping` / `tools/list` / `tools/call`；Bearer token（32 字节随机，写 `ModConfigs/deepspace.bridge.connection.json`）；Host/Origin 白名单；body ≤64KB；5s 读超时；8 并发上限；20s 工具超时 | P0 |
| 2 | `mod/src/ModEntry.cs` | `OnEnable` 启动 adapter，`OnDisable` 释放；token 每次启动更新 | P0 |
| 3 | `game_agent/contracts.py` | 新增 `--export-mcp` 子命令，把 61 个动作 + 只读端点导出成 MCP tools JSON（含 annotations） | P0 |
| 4 | `mod/manifest.xml` | 无需改（已有 `network` + `files`） | — |
| 5 | `README.md` | **重写**，见 §5 | P0 |

**工具集设计**（精选，不必抄它的 36 个）：

- 只读：`game_state`（section + query + offset/limit）、`game_ui`（openPanels，第一阶段可只返回面板列表）
- 动作：`game_action`（action 枚举 + scene 陈旧守卫 + 参数）
- 每个工具带 `annotations`：`readOnlyHint` / `destructiveHint` / `idempotentHint`
- `game_action` 的 `description` 里写纪律（学它）："不接受屏幕坐标""状态变更后重读区域""不要隐式确认弹窗"

**我们的差异化优势**（一定要在简历里讲）：

> 对方的工具定义是**硬编码**在 C# 里的 35 个区域 + 88 个动作枚举；我们的工具 schema 由 `contracts.py` **单一契约源生成**，C# 侧 `GET /contract` 与 Python 侧启动时自动比对——杜绝"模型按提示词输出、校验层拒绝"的漂移问题。这正是我们踩过 59/58/61 三套清单漂移的坑之后做出的设计。

### 阶段 2 · 执行安全三件套（2–3 天，面试加分）

把我们已有的安全机制统一成可讲述的框架：

| 环节 | 现有实现 | 融合后表述 |
|---|---|---|
| 前置校验 | 三层白名单 + 7 个守卫 | **动作前置守卫** |
| 陈旧检测 | 部分有（动画闸门/状态签名） | 搬它的 `scene` 参数：工具调用带上次读取的场景名，不匹配直接拒绝 |
| 执行后验证 | 只认现金/库存/天数 diff | 泛化为**工具级 Verify 回读框架**，`game_action` 返回 `{dispatched, verified, before, after}` |

**简历话术**："设计 Agent 执行安全三件套：动作白名单前置校验 + 场景陈旧状态检测 + 执行后状态回读。成交判定只认现金/库存实际变化，不信任接口返回的 `ok=true`（历史上有假成功）。"

### 阶段 3 · UI 能力补全（可选）

抄 `game_ui.openPanels` 的设计：按窗口前后序列出正文、控件 ID、`actionable`、`closeTarget`；替换我们 `ui_click` 靠坐标点击的路径。这是**功能补全**，简历上作为"支持自绘 UI 的结构化交互"一句带过即可。

## 6. 面试问答准备（提前想好）

**Q：为什么用 MCP，不直接用自己的 HTTP 桥？**
A：自研桥延迟低但生态封闭，MCP 是行业标准、任意 AI 客户端即插即用。两个并存是"内部闭环用快协议、外部生态用标准协议"的取舍，不是重复建设。

**Q：为什么工具 schema 要由契约源生成？**
A：我们踩过坑——ACTIONS 59 条、参数表 58 条、C# case 61 条，模型照提示词输出但校验层拒绝。所以做了单一真相 + 启动时双向比对，不一致直接告警而不是静默降级。

**Q：为什么直调游戏 API，而不是模拟玩家输入？**
A：直调快、一步到位；但需要自建守卫体系补偿"跳过 UI 前置条件"的副作用。模拟输入保真但慢且锁版本。我们选了前者，并用三层守卫 + 回读验证管住风险。

**Q：多智能体怎么避免写冲突？**
A：每个角色有独占文件写权限，跨角色改动走"变更请求"，交接物是具体文件 + 验证命令，不是口头报告。

**Q：踩过最大的坑？**
A：V5 实机一次抓出三个离线全绿时看不见的问题——`.bak` DLL 被扫描器当载荷拒载、`ModHelper` 在 `OnEnable` 时未就绪导致 accept loop 从不启动、手写 JSON 不还原 `\uXXXX` 使所有中文参数失效。教训是"离线全绿不算数，实机才能证伪"。

## 7. 风险与边界

1. **不要动现有决策链**。阶段 1 的 MCP adapter 是纯增量，不改 `agent_loop.py` / `brain/*` / `contracts.py` 的运行时行为（只加导出命令）。
2. **不要为了"像它"而把 61 个动作改成 88 个**。数量不是亮点，契约设计才是。
3. **token 不要写死在配置文件里**，每次启动随机生成并写入 `ModConfigs/`，退出时清理（学它的做法）。
4. **兼容性**：`manifest.xml` 已有 `network` + `files` 能力，新增回环监听不需要改能力声明；12-10 硬截止已处理完。
5. **如果目标岗位是游戏 Mod/逆向**，则 §2 的结论反转——虚拟输入 + Harmony IL 补丁应作为主亮点，MCP 降为配角。
