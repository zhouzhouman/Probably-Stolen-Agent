## §6 第三轮：剩余项收口（mod v3.3.0）

### 6.1 机器逐类配方（已做）

正式版的配方**不在机器类里写死**，而是挂在机器物品自身：`GameItem.recipeManager`
（`CraftingRecipeManager.availableRecipes`）。因此不需要 "54 个机器类逐个摸"——
统一从物品取即可。

`/machines` 每台机器新增 `recipes[]`：

```
{"name": 配方名, "tools": [...], "materials": [{name, amount, ids?, tags?}]}
```

过滤器分三类，已分别处理：
- `CraftingIdentifierFilter.identifierFilter` → `ids`
- `CraftingTagsFilter.tagFilter` → `tags`
- `CraftingCustomFilter` → 只有显示名（判定是 lambda，静态不可展开）

**刻意不提供产出**：产出由 `craftFunc` 运行时计算，静态读不到。编一个"产出"比不给更糟。

### 6.2 枪械订单专用动作（已做）

新增 `accept_gun_order`（ACTIONS 57 / 参数表 56）：

1. 取当前顾客的 `gunOrderData`，没有则提示看 `client.gun_order`；
2. 用游戏自己的 `IsAccepted()` 判定；不满足时**逐条列出未达标的必选需求**，
   且**不调用任何游戏接口**（避免"点了接受但交不了货"）；
3. 满足后才调 `NegociationUIManager.OnOfferAcceptClick()`。

观察层同步加提示：订单可交 → 明确建议 `accept_gun_order`；不可交 → 列出缺什么并禁止硬交。

### 6.3 战斗（决定不做动作）

`CombatEntityBuilder` / `Creature` 等类在正式版存在，但玩家的战斗是射击小游戏
（`unlocks.shooting` + `state.shooting`）。在 `--no-mouse` 约束下无法瞄准，
做"战斗动作"等于制造必然失败的接口。**结论：只保留 `shooting` 状态暴露，不新增战斗动作。**

### 6.4 旧卡复核（产出工单 + 抽样核对）

无法自动判定"试玩版数值在正式版是否仍成立"，因此改为两件事：

1. **工单**：`scripts/knowledge_staleness.py` → `artifacts/knowledge_review.md`
   按风险排序（wiki-only 且有数值 +3、触发器指向新段 +2、未复核 +2、无 verified_at +1、已废弃 -5）。
   当前：**200 张卡 / 高风险 158 / 中风险 20**。
2. **抽样核对**（用实机 `/state` 与反编译源码）：
   - `criminal-network-referral`：CRIMINEL_NETWORK cost=45 ✅ 一致
   - `contact-buyer-referral`：BUY_REFERAL cost=10 ✅ 一致
   - `faction-objects-six`：源码有 **8** 个派系常量、实机只返回 **5** 个、卡片说 **6** 个
     → 三个口径不一致，**不猜**，写 `review_note` 待人工实测
   - `network-contacts-table`：正式版已无 `networkUpgrade` 字段 → 标 `review_note` 不可作决策依据

- `pytest -q` → **610 passed**
- `audit_cards.py` → 0 严重问题
- mod **v3.3.0** 已部署（145,408 字节），DLL 编译 0 警告 0 错误

## §7 第四轮：把"知道"变成"能算账"（mod v3.5.0）

前三轮解决的是"看得见新内容"，这一轮补的是**看得见但用不上**的部分——
字段有了，模型还是得靠猜，那等于没有。

### 7.1 难度不再只是标签

`difficulty` 段新增 `rules`：`retail_markup` / `rent_increase` / `power_mult` / `insurance_mult` /
`property_base_price` / `permit_fee` / `appraisal_join_cost_mult`，都取自 `Difficulty.Rules`
（本局真实生效值）。此前只给 `id`+`title`，模型知道是 hard 也照样按 normal 定价。

### 7.2 夜间事件给出"改了什么"

`afterhour_events[]` 新增 `effects[]`：`text`（人话）/ `polarity`（正负）/
`modifier_key`+`modifier_value`（机器可读修正）。此前只有标题，模型不知道"停电"到底影响什么。

### 7.3 机器投料两道保险

1. **落位**：`machine_put` 原来用裸 `UncheckedAccept`，与 `stow_loot` 的 P1 同因——
   会把物品叠进已有物品那一格。改走 `TryPlaceInto`（找空位→改原点→`ValidateShapeState`
   →`CheckShapePlacement`→入库），失败时把物品放回原容器。
2. **配方提示**：投料后用 `CraftingFilter.Filter(item)` 逐条比对配方材料/工具，
   不匹配则返回里附"该物品不在本机任何配方里"——**只提示不拦截**，因为电池/模块槽不在配方内。

### 7.4 修掉一个迁移遗留 bug（重要）

`_next_step_hints` 里判断"人是否在拾荒点"仍在比 `current_location == "SCAVENGING"`，
而正式版已经是 `dumping_ground` 这种 id ——**拾荒提示在正式版完全失效**，
而且不会报错、只表现为"AI 到了拾荒点却不继续拾"。已改为同时接受两种写法，并加回归测试。

### 7.5 提示系统扩容

新增四类确定性提示：按揭本周不够现金、今晚地点被事件关闭、鉴定升职待处理、枪械订单可交/不可交。
提示上限由 6 提到 8——6 条时忙碌局面会把"今晚该出门拾荒"这类提示挤掉，那是最贵的丢失。

### 7.6 质检

- `pytest -q` → **615 passed**（新增 5 条提示测试，含拾荒地点 id 回归）
- `audit_cards.py` → 0 严重问题；知识卡 201 张（新增 `machine-recipes-data`）
- mod **v3.5.0** 已部署（147,968 字节）；DLL 0 警告 0 错误

1. **实机验证**：v3.3 之后的所有改动（配方 / `accept_gun_order` / 事件 effects / 难度 rules）
   都还没在真机跑过——这是当前最大的风险敞口。
2. **158 张高风险知识卡**逐张复核（工单在 `artifacts/knowledge_review.md`）。
