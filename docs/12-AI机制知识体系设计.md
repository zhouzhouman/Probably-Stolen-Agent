# 让 AI 掌握全部机制：现状诊断与机制知识体系设计（v2.2）

> 问题：AI 目前只会「交易、拾荒」这类最基础的操作，无法理解游戏的全部机制。
> 本文回答四件事：**现在的机制知识是怎么存在的 → 应该怎么组织 → 决策时怎么调用 →
> 还缺什么、怎么补、补完什么效果**。
>
> 本次已落地一个可运行的最小实现：`game_agent/knowledge/` + `knowledge/mechanics/`
> （10 张机制卡）+ `cli knowledge` + 24 项测试；全量回归 **545 passed**。

## 一、现状：机制知识实际散落在 5 个地方

| 载体 | 规模（实测） | 更新方式 | 局限 |
|---|---|---|---|
| 静态提示词 `brain/prompt.py::BRIDGE_ACTION_TOOLS` | **13,547 字符 / 284 行** | 改代码 | 线性文本、无法检索；动作说明、策略、历史教训混在一起 |
| 硬编码守卫 `agent_loop.py` | **8 个**（category / dialog / inventory / morning_report / night_ui / pre_action_state / rent_reserve / shutter） | 改代码 + 测试 | 知识是「命令式」的，只有拦截没有解释；AI 看不到为什么被拒 |
| 桥接动作 `/action` | **48 个**（Python 白名单） | 改 C# + Python | 有动作但缺「何时用、用了会怎样」 |
| 状态字段 `/state` | **26 个顶层字段** | 改 C# | 部分字段根本没进观察层（见下） |
| 文档 / 日志 / 记忆 | 12 份 docs + play_journal + MEMORY.md | 人写 | 给人看的，AI 读不到 |

### 三个断点（都有实盘证据）

**A. 观察断点：状态字段有，AI 看不到。**
`/state` 实际返回 `reputations`（5 个派系）、`requests`（派系委托）、`unlocks`
（`shooting` / `vending_machine` / `gene_scanner` 等解锁位），但 `build_observation()`
的 `visible_info` **一个都没接**。结果是：

- `fill_request` 动作在白名单里，AI 却看不到任何委托 → 这个动作永远想不起来用；
- 举报通缉犯会掉派系声望，AI 看不到声望数值 → 无法权衡；
- `unlocks.shooting=false`（射击未解锁），AI 不知道「现在还不能开枪」。

**B. 组织断点：知识是线性文本，不能按局面取用。**
单步提示词实测 **37,102 字符**（观察 15,826 + 动作说明 13,547 + 规则/历史/目标）。
继续往里加机制会同时踩两个坑：token 成本线性上涨；长上下文里中段信息最容易被忽略
（这就是为什么「批发按钮是买入」写在 284 行中间时，模型照样点错，净亏 62）。

**C. 验证断点：知识没有来源、置信度、失效时间。**
`AcceptWholesale` 的方向，代码里的租金守卫当成「买入」拦，提示词却写成「卖出」——
两套知识互相矛盾，直到实盘亏了 62 元才被发现。知识不可审计，就无法自动发现腐化。

### 一个「看起来像缺口、其实是设计」的动作

~~C# 桥接实现了 `toggle_power`，但 Python 白名单没有它，模型永远调不到。~~
**v3.0 更正**：读 `BridgeApi.cs` 实现可知，`toggle_power` 已被**刻意废弃**——它只返回
`Err("电源不能在日间直接切换")`，因为游戏电力由夜间服务 `POWER_SERVICE` 驱动，
直接翻转 `ps.isPowerOn` 会与真实状态脱节。所以这不是动作缺口，是正确设计。
真正缺的动作是远征、雇工、机器操作、彩票、治疗、贿赂（见 `docs/13` 第七节）。

## 二、目标：机制掌握的四层能力

| 层级 | 能力 | 判定标准 | 当前 |
|---|---|---|---|
| L1 知道 | 说得出规则 | 卡片里有 facts | 部分（13.5KB 文本） |
| L2 看懂 | 从状态识别「现在处于哪个机制」 | 触发器命中率 | 几乎没有（无触发器） |
| L3 会做 | 给出合法动作序列与前置条件 | 动作链成功率 | 部分（守卫兜底） |
| L4 会验 | 动作后核对后果、发现知识失效 | effects 核对/告警 | 没有 |

只有 L1 的知识 = 背书；只有 L1+L2 = 能解释；L1~L4 齐全才算「掌握」。

## 三、机制信息怎么组织：三层 + 一张卡

### 3.1 三层结构

```
L0 原子事实（state dictionary）
   /state 每个字段的含义、取值范围、更新时机
   → 由 C# 与观察层保证；文档化在 knowledge/state_fields.json（待补）

L1 机制卡（mechanic cards）        ← 本次落地
   一个机制一张卡：触发条件 / 事实 / 动作 / 禁忌 / 后果 / 证据 / 置信度
   → knowledge/mechanics/<category>/<id>.json

L2 策略剧本（playbooks）           ← 待补
   面向目标的跨机制组合：十日千元 / 交租周 / 拾荒夜 / 违禁品冲量
   → knowledge/playbooks/*.json（引用卡片 id，不重复事实）
```

### 3.2 机制卡 schema（已实现并有校验）

| 字段 | 作用 | 示例 |
|---|---|---|
| `id` | 唯一标识（小写 slug） | `wholesale-direction` |
| `category` | 12 类之一 | `trade` |
| `triggers` | **什么时候该出现**：对观察的谓词（all/any） | `table.nego_buttons.wholesale` truthy |
| `facts` | 机制事实（必须≥1条） | 「wholesale_cost 是我方要付的钱」 |
| `actions` | 正确动作序列 | 「卖货走 accept_offer / sell_item」 |
| `pitfalls` | 踩过的坑（带实证） | 「当卖出按钮点，净亏 62」 |
| `effects` | 可观测后果（用于事后核对） | 「现金减少=买入成功」 |
| `guards` | 硬前置条件（可编译成代码） | 「现金 ≥ rent_due×3 才允许大额进货」 |
| `evidence` | 反汇编/日志/实盘证据 | 「r101 现金 14,425→14,263」 |
| `confidence` / `verified_at` | 置信度与最后验证时间 | `0.98` / `2026-10-24` |
| `related` | 关联卡 | `["customer-buying-tags"]` |

**为什么用触发器而不是纯语义检索**：这款游戏的状态是强结构化的（`/state` 26 个字段），
「现在是不是批发场景」用 `nego_buttons.wholesale == true` 判定，比向量相似度**确定、可解释、
零依赖**。语料只有几十张卡，不需要向量库；超过 500 张再考虑 BM25/embedding 混合。

### 3.3 分类体系（12 类，覆盖全部系统面）

`loop / trade / customer / economy / security / night / phone / quest / production /
store / risk / meta`

本次种子卡 10 张，已覆盖 8 类：日循环、批发方向、顾客类别、估价、租金、通缉举报、
夜间服务费、拾荒收纳、鱼场产能、派系委托（观测缺口示例）。

## 四、机制信息怎么传给 AI：常驻索引 + 按需检索 + 编译守卫

| 通道 | 内容 | 预算 | 频率 |
|---|---|---|---|
| ① 常驻索引 | 一行一张卡（id + 标题 + 分类） | ≤300 字符 | 每步（默认关闭） |
| ② 按需卡片 | 触发器 + 关键词命中的 1~3 张完整卡 | ≤1,800 字符 | 每步 |
| ③ 编译守卫 | `guards` 编译成 Python 断言 | 0 token | 动作前 |
| ④ 事后核对 | `effects` 与动作结果比对 | 0 token | 动作后 |
| ⑤ 反馈回写 | 命中/失败/矛盾 → 置信度与 `verified_at` | — | 每批 |

检索打分（已实现）：

```
score = 触发器分（10 + 2×命中数）×2 + 关键词命中数×2 + 置信度×0.5
入选门槛 min_score = 3.0
```

两条关键工程约束（都是踩坑后加的）：

1. **关键词只匹配「值」，不匹配字段名**。否则 `rent_due`、`sellable_now` 这种字段名
   会让对应卡片永远命中（实测：租金卡在没有任何租金事件时也常驻）。
2. **置信度只做同分微调**。早期把 `confidence×3` 当基础分，结果「一个泛词 + 0.97 置信」
   就能压过「触发器命中」——检索退化成噪音。

本次 `cli knowledge --select` 在无顾客、非批发、非夜间的状态返回 **0 张**（不注入噪音）；
在有批发按钮时正确返回 `wholesale-direction`，在有通缉犯时返回 `wanted-report`。

## 五、决策时怎么调用：三段式

```
观察 /state
   │
   ├─(1) 机制检索：trigger + keyword → 1~3 张卡 → 提示词「【机制知识】」段
   │      作用：把「此刻相关的规则/禁忌/后果」放到模型注意力最近处
   │
   ├─(2) 动作前守卫：cards.guards + 既有 8 个硬守卫
   │      作用：非法动作在发出前被拦下，detail 里带「为什么」（来自卡片 facts）
   │
   ├─(3) 动作后核对：cards.effects vs /state 差分
   │      作用：现金没变=没成交、库存没加=钱货两失；矛盾则降置信并告警
   │
   └─(4) 步骤记录：step["mechanics"] = 命中卡 id
          作用：复盘时能回答「这一步 AI 依据的是哪条机制」
```

### 与现有 8 个守卫的迁移关系

| 现有守卫 | 对应机制卡 | 迁移方式 |
|---|---|---|
| `_rent_reserve_guard` | `rent-lease` | 卡片 `guards` 声明阈值，守卫读卡片参数 |
| `_category_guard` | `customer-buying-tags` | 保留代码，卡片提供解释文案 |
| `_inventory_guard` | `customer-buying-tags` | 同上 |
| `_shutter_guard` / `_night_ui_guard` | `day-cycle` | 阶段规则进卡片，守卫只做校验 |
| `_morning_report_guard` | `day-cycle` | 卡片记录面板关闭路径 |
| `_pre_action_state_guard` | `day-cycle` | 状态机进卡片 |
| `_dialog_guard` | `customer` 类新卡（待补） | 特殊 NPC 规则卡 |

原则：**卡片负责「解释与检索」，代码负责「不可绕过的硬约束」**；两者共享同一份参数，
避免再次出现「提示词说卖、代码当买」的矛盾。

| 来源 | 能拿到什么 | 工具/方法 | 产出 |

| Wiki / 指南 | 设计意图、隐藏规则 | 人工整理 | 待验证假设 |
| 实盘实验 | 唯一能定因果的证据 | `run_to_goal.py` + `step` 记录 | `evidence` + 置信度 |

**半自动补全流程（建议做成 P1 脚本）**

```
dump.cs ──► 候选字段/方法清单 ──┐
GameLog ──► 事件类型统计 ───────┼──► 人工判定 ──► 卡片 JSON ──► CI 校验 ──► 上线
存档 diff ─► 状态变量变化 ──────┘                              │
                                                               └─ 动作名必须在 ACTIONS
                                                                 字段必须在 /state
                                                                 触发路径必须可解析
```

CI 校验（可立即加）：
- `id` 唯一、`category` 合法、`facts`/`evidence` 非空；
- 卡片里引用的每个动作名 ∈ `bridge.client.ACTIONS`；
- `triggers` 的 `field` 在最近一次 `/state` 快照里可解析（允许 `null`，但不允许拼错）；
- `verified_at` 超过 30 天 → 置信度衰减 0.1（游戏更新会让知识腐化）。

| 提示词里的机制部分 | 13,547 字符（不可检索） | ≤1,800（按需） | ≤1,800 + 索引 300 | 单步 |
| 知识矛盾发现方式 | 实盘亏钱后人工发现 | effects 自动告警 | 自动告警 + 置信衰减 | B10 类 |
| 空转/无效动作占比 | 历史批次约 10~25% | 降低 30% | 降低 50% | 步数/成交比 |
| 新机制上手成本 | 改 13KB 提示词 + 改代码 | 写一张 JSON | 自动生成候选 + 人审 | 交付周期 |
| 单步延迟（检索） | — | +5~15ms | +5~15ms | 纯本地匹配 |

**最关键的变化不是「AI 多知道几条规则」，而是：**
- 规则从「埋在 284 行中间、模型看不到」变成「此刻相关才出现、出现在最近的位置」；
- 每条规则有证据、置信度、验证时间，**能被审计、能被证伪**；
- 动作前有解释、动作后有核对，机制知识第一次形成闭环，而不是单向灌输。

## 十、风险与边界

| 风险 | 表现 | 对策 |
|---|---|---|
| 卡片腐化（游戏更新） | 旧规则误导 | `verified_at` 衰减 + effects 漂移告警 |
| 检索漏召回 | 关键时刻没给卡 | 触发器 + 关键词双通道；`--select` 抽查；关键卡可设 `always` |
| 检索噪音 | 泛词卡片常驻 | 只匹配值、不匹配字段名；置信度不做基础分；`min_score` 门槛 |
| 知识过载 | 3 张卡仍太长 | 单卡 ≤1.8KB；渲染截断；策略层引用卡片而不重复事实 |
| 卡片与守卫冲突 | 一个说卖、一个当买 | 守卫参数从卡片读取；冲突进 CI |
| 触发器写错 | 永不命中/误命中 | 载入时校验路径；`--validate` + 真实局面抽查 |

**边界**：机制卡不能替代探索。未知机制（剧情分支、隐藏解锁）仍要靠实盘实验与
dump 反汇编发现；知识库的作用是**把已发现的知识变成可复用资产**，而不是凭空产生知识。

## 十一、现在就能验证的三条命令

```bash
# 1. 校验全部机制卡（schema / 分类 / 触发器算子 / 事实与证据）
python -m game_agent.cli knowledge --validate

# 2. 看某张卡的完整内容（事实/动作/禁忌/后果/证据）
python -m game_agent.cli knowledge --id wholesale-direction

# 3. 用当前真实局面检索（游戏运行走 bridge，否则走存档快照）
python -m game_agent.cli knowledge --select
```

输出示例（本次实测，无顾客/非批发状态）：

```
机制卡 10 张，命中 0 张：（无）      ← 不注入噪音
```

开启后，每一步的 `artifacts/steps/step_*.json` 会多一个 `mechanics: ["wholesale-direction"]`
字段，复盘时能准确回答「AI 当时依据的是哪条机制」。
